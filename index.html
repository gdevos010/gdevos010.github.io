My AI agents write the code. A queue decides what lands.

I stopped being a merge clerk for my own AI agents. Here's what replaced me, what 20 days of it looked like, and what I'd steal from it

I build a desktop app mostly by running Claude Code sessions in parallel, each on its own branch. Writing the code scaled fine. What didn't scale was me. Every branch needed a review, the full test suite on macOS, Windows and Linux, and a pile of screenshot checks. Then someone had to merge it, notice main had moved, and do half of it again. At the rate branches land now, 11 a day and 20 on a busy one, that's a full-time job as a merge clerk.

Attempt one: tell an agent how to do it

The obvious fix was to write down how to land a branch (merge it into main once it's checked) and let an agent do the clerking. The instructions grew to 14,440 words. Keeping them working took 157 commits in two weeks, because every review found another place where a rule was missing. "Look at the git server again before you merge" had been copied into about nine places, and there was always one more that needed it.

The lesson: a state machine written as prose doesn't hold together.

Attempt two: code runs the loop, AI makes the calls

So I split the job in two.

Plain, tested code runs the loop. A Mac, a Windows PC and (lately) a Linux server each run a worker. On every pass, a worker reads each branch's facts from git and walks one ordered list of rules; the first rule that matches is the branch's next step. Nothing is stored outside git, so a crash or a reboot is designed to cost a retry, never a wrong merge. The machines never talk to each other, only to the git server.

AI does only the judgment calls: reviewing a branch, fixing what the review found, resolving a merge conflict the code can't, writing up changed screenshots for me. Each is a fresh session with one job and no memory. It commits, and the code checks the work before pushing. Every review finding gets fixed, each fix needs a test that failed first (or a reviewed reason why none can), and the fixes get one review, not an infinite regress.

A coding session's last step is now to hand its branch to the queue ("enqueue"). After that I don't touch the branch unless the queue asks me to, or I choose to step in.

Five things I'd steal from it

1. Let branches land in any order. When a check passes, the queue commits a small record (a stamp) naming the check and the commit. Only the branch's own later changes make a stamp out of date, never what main brought in. My first version re-checked every branch whenever anything landed, which made order matter and everything wait. Now main itself gets checked once after each landing, and a failure there becomes a new fix branch.

2. Write your decisions down where agents must look. An AI session has no memory, so a choice I made last week looks like odd code to the next session, and a reviewer will happily "fix" it. Every ruling I make goes into a dated decisions log. Reviewers are told to search it before filing a finding; a fix that needs a decision the log doesn't cover comes to me as a question instead of a guess; and when the code breaks a rule the log states, the code is what's wrong. It only works as well as I keep the log.

3. Expect the queue to be its own biggest project. 106 of the 214 landings (50%) changed the queue's own code, tests or prompts. Mostly that was me: 98 of them came from sessions I started, and the automatic improvement loop has landed exactly 2 branches so far. The loop is still worth having. Every failure is logged, a small, cheap model (Haiku) files each bad landing against a list of known problems, a scheduled task opens improvement branches from the top of that list, and since 10 Nov Haiku and the big model (Opus) have been reading old transcripts for process problems, with any change they propose held for my approval. Flaky tests (ones that fail at random and pass on a rerun) are the other tax: 18% of all landings were the queue fixing them, on their own branches, instead of quietly retrying.

4. Machine time is cheap; waiting isn't. A median branch got 2.9 hours of machine work and waited a median 17 hours to merge. That wait tracked the queue: 6 hours with fewer than 5 other branches queued, 35 with 20 or more. Little's law would have told me as much, but seeing it in my own numbers changed what I look at: the queue, and the time branches spend waiting on me, which my records can't yet split out.

5. One machine can stall everything. A queue that needs every machine to agree is only as available as its least available machine. When the Windows PC ran low on disk, nothing landed through the queue for 44 hours, and I cleared the pile-up by hand, skipping the checks (17 of my 19 hand landings in the period).

How it's going

In 20 days the queue landed 214 branches: 172 from my coding sessions, the rest its own fixes and improvements. 164 of them never got stuck waiting for me; 50 did at least once. I still approve every screenshot change by hand. It all runs on those three machines and one Claude Max subscription.

What I don't know yet is whether the code that landed is any good. The records measure speed and how often I was needed, not the bugs that got through. That's the next thing I want to measure. Until then, the full report has the mechanism, every chart's data to download, and the limits of what the numbers can say. It's layered: its first screen gives the gist in 30 seconds, its summary the mechanism in five minutes, and the rest the evidence.
