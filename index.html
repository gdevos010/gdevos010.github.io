My AI agents write the code. A queue decides what lands.

I stopped being a merge clerk for my own AI agents. Here's what replaced me, what 20 days of it looked like, and what's worth stealing from it

I build a desktop app mostly by running Claude Code sessions in parallel, each on its own branch. Writing the code scaled fine. What didn't scale was me. Every branch needed a review, the full test suite on macOS, Windows and Linux, and a pile of screenshot checks. Then someone had to merge it, notice main had moved, and do half of it again. At the rate branches land now, 11 a day and 20 on a busy one, that's a full-time job as a merge clerk.

Attempt zero: do it all myself

It started as a chore, not a project. Each check left a stamp, a small committed record naming the check and the commit it passed on, and I ran every screenshot render and wrote every stamp by hand, on the Mac, then again after switching to the Windows PC. A stamp counted only on the exact commit it named, so merging the latest main into a branch made all of its stamps stale and I started over. I couldn't work on two branches in parallel at all: landing one sent the other back to the beginning.

Attempt one: tell an agent how to do it

The obvious fix was to write down how to land a branch (merge it into main once it's checked) and let an agent do the clerking. The instructions grew to 14,440 words. Keeping them working took 157 commits in two weeks, because every review found another place where a rule was missing. "Look at the git server again before you merge" had been copied into about nine places, and there was always one more that needed it.

The lesson: a state machine written as prose doesn't hold together.

Attempt two: code runs the loop, AI makes the calls

So I split the job in two.

Plain, tested code runs the loop. A Mac, a Windows PC and (lately) a Linux server each run a worker. On every pass, a worker reads each branch's facts from git and walks one ordered list of rules; the first rule that matches is the branch's next step. Nothing is stored outside git, so a crash or a reboot is designed to cost a retry, never a wrong merge. The machines never talk to each other, only to the git server. That isn't a purity rule: they aren't on the same network, and the git server is the one place all three can reach. On one network, a single machine handing out the work would have made most of this much simpler.

Who talks to whom

Arrows into the git server are pushes and reads; the arrow to the fresh AI sessions starts them, and the dashed arrow is a phone notification. The workers never talk to each other, only to the git server.

After enqueue the queue needs me only for approvals, help with a stuck branch, and exceptions; I can also put a branch first or restart a stuck one on my own call.

AI does only the judgment calls: reviewing a branch, fixing what the review found, resolving a merge conflict the code can't, writing up changed screenshots for me. Each is a fresh session with one job and no memory. It commits, and the code checks the work before pushing. Every review finding gets fixed, each fix needs a test that failed first (or a reviewed reason why none can), and the fixes get one review, not an infinite regress.

A coding session's last step is now to hand its branch to the queue ("enqueue"). After that I don't touch the branch unless the queue asks me to, or I choose to step in.

Five things worth stealing

The report has seven; these are the five I'd defend hardest.

1. Let branches land in any order. This is the fix for attempt zero. The queue still commits a stamp when a check passes, but only the branch's own later changes make it out of date, never what main brought in. My first version re-checked every branch whenever anything landed, which made order matter and everything wait. Now main itself gets checked once after each landing, and a failure there becomes a new fix branch.

2. Write your decisions down where agents must look. An AI session has no memory, so a choice I made last week looks like odd code to the next session, and a reviewer will happily "fix" it. Every ruling I make goes into a dated decisions log. Reviewers are told to search it before filing a finding; a fix that needs a decision the log doesn't cover comes to me as a question instead of a guess; and when the code breaks a rule the log states, the code is what's wrong. It only works as well as I keep the log.

3. Expect the queue to be its own biggest project. 106 of the 214 landings (50%) changed the queue's own code, tests or prompts. That's the improvement loop, and it has more parts than any one script. Every failure is logged. A stuck branch pings me. A cheap model (Haiku) files each bad landing against a list of known problems, and a scheduled task opens improvement branches from the top of that list. Since 10 Nov, models also read old transcripts for process problems; anything they propose waits for my approval. Most of the fixing still happens in sessions I start (98 of those 106 landings); the scheduled task has opened 2 so far. Flaky tests (ones that fail at random and pass on a rerun) are the other tax: 18% of all landings were the queue fixing them, on their own branches, instead of quietly retrying.

4. Watch what you enqueue against what lands. A branch's wait is the number I feel, but it's a poor measure of the queue: it counts every hour the branch waited for me, and a screenshot approval asked for in the evening waits until morning. So I watch two counts instead, branches enqueued and branches landed. The queue landed 11 on a median full day, up to 20, a little less than I fed it, so the line grew. Whether the queue couldn't go faster or I never pushed it harder is in its logs, which record every ready branch it held and why; I haven't pulled that out yet.

5. One machine can stall everything. A queue that needs every machine to agree is only as available as its least available machine. When the Windows PC ran low on disk, nothing landed through the queue for 44 hours, and I cleared the pile-up by hand, skipping the checks (17 of my 19 hand landings in the period).

How it's going

In 20 days the queue landed 214 branches: 172 from my coding sessions, the rest its own fixes and improvements. 164 of them never got stuck waiting for me; 50 did at least once. I still approve every screenshot change by hand. It all runs on those three machines and one Claude Max subscription.

What I don't know yet is whether the code that landed is any good. The records measure speed and how often I was needed, not the bugs that got through. The only signals in them are thin: one landing fixed a failed check of main, and git shows two reverts on main in the period, one of them of a branch I'd landed by hand. Neither ties a later fix back to the landing that needed it, so I don't count them as a quality measure yet. That's the next thing I want to measure. Until then, the full report has the mechanism, every chart's data to download, and the limits of what the numbers can say.
