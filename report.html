My AI sessions finished branches faster than I could check and merge them

Here's the problem the queue solves, and the one rule it enforces.

I build a cross-platform desktop app mostly by running many AI coding sessions (Claude Code) at once. Each one works in its own copy of the repository, on its own branch. Before a change reaches main it should pass a code review, the full test suite, and screenshot comparisons on macOS, Windows and Linux: screens drawn in a headless browser, and screens drawn by the real app. With a dozen or so branches a day to land, and 28 on the busiest, doing that by hand stopped being engineering and became bookkeeping: which branch is where, which machine needs a command typed, what to rerun because main moved.

It started with me doing exactly that: running each screenshot render and writing each check's stamp (its pass record) by hand, switching between the Mac and the Windows PC. A stamp counted only on the exact commit it named, so merging main into a branch made every stamp stale, and I couldn't keep two branches going in parallel.

My first fix was to hand the bookkeeping to an agent: 14,440 words of written instructions for landing a branch. It took 157 commits in two weeks to keep them working, because every review found another place where a rule ("look at the git server again before a merge") was missing. A state machine written as prose doesn't hold. So I rewrote it as tested code, kept AI for the judgment calls, and called it the land queue (from "landing" a branch on main).

Now a session's last step is to push its branch and enqueue it, which adds an empty marker commit. After that, nobody tracks the branch or merges it by hand, me included, except in the cases listed under My part, my rulings. The queue merges a branch only when four things hold at its latest commit:

  1. Reviewed. An AI review covers every commit of the branch's own.
  2. All six checks current: the test suite, headless-browser screenshots and real-app screenshots, on the Mac and on the Windows PC. The PC's queue runs under Linux (WSL): its tests and headless screenshots run on Linux, and its real-app check on Windows. Since 4 Nov, a separate Linux server also runs the full suite first, as a pre-check.
  3. The merge into main is clean. A conflict is resolved on the branch first, and the resolution is checked like any other change.
  4. No screenshots waiting for my approval.

Who talks to whom

Arrows into the git server are pushes and reads; the arrow to the fresh AI sessions starts them, and the dashed arrow is a phone notification. The workers never talk to each other, only to the git server.

After enqueue the queue needs me only for approvals, help with a stuck branch, and exceptions; I can also put a branch first or restart a stuck one on my own call.

Plain code, not an agent, decides each branch's next step, working it out again from git every time

How a worker picks what to do, and why it keeps no state of its own.

Three machines run a queue worker each: a Mac, a Windows PC, and (since 4 Nov) a Linux server. They never talk to each other directly, because they aren't on the same network; with one network, a single coordinator handing out work would have been much simpler. The git server is the one place all three can reach, so it is their only channel: branches, marker commits, and small notes kept under git refs that branches don't use. Each pass of a worker goes like this:

  1. Look at the git server: a cheap look for moved branches every 2 minutes on the Mac and Windows and every 10 seconds on the Linux server, and a full fetch every 5 minutes.
  2. For each enqueued branch, read its facts from git: its commits, review markers, stamps (the record of a passed check, below), and the notes other workers left.
  3. Feed those facts to one function with no side effects. It walks a fixed list of rules and returns the first that matches: the branch's next action on this machine.
  4. Shared work (review, fixes, catch-up, merge) goes to one worker: it claims the branch by writing a note on the git server that fails if another worker got there first. The claim is renewed every 10 minutes and taken over by another worker once it is 30 minutes old, so a dead machine can't hold a branch. Checks need no claim: each machine runs its own.
  5. Run it. A worker runs one check or merge at a time and up to 3 AI sessions alongside (8 on the Linux server, which takes the same AI steps, catch-ups and merges as the others, plus the pre-check, but has no stamped checks of its own). Then look again.

Because nothing lives outside git, any worker, or I, can pick up a landing from what git shows after a crash, a reboot or a deleted local file. And each rule lives in one place, which is what the prose version never managed.

AI does only the judgment calls, each in a fresh session with one job

The queue's AI steps, and the rules that keep them honest.

Every step that needs judgment starts a new headless Claude Code session with one prompt and one job. No session lives across steps or remembers anything: the code passes it what it needs and reads back what it committed. Sessions commit but never push; the code pushes, after checking what they did. A landing used a median 9 of these.

Most sessions time out after 2 hours, Simplify after 4.

Three rules govern review and fixes:

  • Fix everything, ask nothing. The rule is that every finding gets fixed, whatever its severity, and I'm never asked whether to skip one. A finding goes to the backlog (my list of deferred work) for only four reasons: it needs a product decision from me, it needs hardware the fixer lacks, two tries to fix it failed, or it's a cleanup outside the branch's own lines.
  • A fix is proven red, then green. Its test must fail without the fix and pass with it. When no test can fail, the session says why, and the review of the fixes judges that reason.
  • The review stops. The fix commits get one review, for correctness only, and one last round of fixes follows without another review. Reviews of reviews never chain.

Rules pick how deep the review goes. A branch that touches risky paths (stored data and its migrations, the queue's own code and prompts, configuration, lockfiles), deletes a test, weakens a check or changes an assertion always gets the full review. Otherwise a triage session answers seven yes-or-no questions, and seven noes get the light review. A light review that finds a critical problem in the branch's own files is raised to full.

A passing check is stamped on a commit, so branches can land in any order

The stamp is what lets six checks on two machines add up to one decision.

A stamp is a small file committed on the branch: the check's name and the commit it passed on. A check that passes writes its stamp and pushes it. A stamp goes stale only through the branch's own changes since that commit:

  • its own commits count in full;
  • for a merge of main into the branch (a catch-up), only what the conflict resolution changed counts;
  • what main brought never counts.

Each check also names the paths it reads, so a change to a design doc doesn't make the screenshot stamps stale.

My earlier rule made every stamp stale whenever main moved. That made landing order matter: each landing sent every other branch back to be checked again, and my fix for that (batching branches into trains) raised more questions than it answered. Under the current rule, branches are independent and land in any order. A branch waits for another only when told to, or when it holds that branch's commits.

Don't read a stamp as "passes on today's main"

A current stamp says the branch's own changes passed. It doesn't say the branch passes with every change main got since. That gap is closed after the merge, by checking main itself, and any failure is fixed forward on a new branch.

Four more pieces close the gap that the any-order rule leaves:

  • Catch-up is a merge, never a rebase. Code resolves routine conflicts (stamps keep the branch's side, screenshot baselines keep main's, generated files are regenerated). Anything else goes to an AI conflict session, and the result is compiled before it's committed. When only a catch-up made the test stamp stale, only the test suites the resolved files reach run again.
  • Catch-up comes last. The check that the branch contains main's latest commit is the last rule before merge, so main moving during an hour of checks costs one catch-up, not one per landing.
  • A pre-check on the Linux server runs the full test suite before the Mac and Windows spend an hour on theirs. It writes no stamp: a Linux pass never makes a branch landable by itself.
  • main is checked after every landing, once per machine, without blocking anything. A failure becomes a new fix branch, enqueued like any other, and fixed on the machine where it failed.

A pre-push git hook, installed in every checkout, refuses a push to main whose landing lacks current stamps or a review, whoever pushes. This hook and the approval command below both guard against mistakes, not against someone determined; neither is a lock.

I step in only to approve screenshots, help stuck branches, and land a branch myself by exception

What still reaches me, how my decisions are kept once I've made them, and how the queue keeps those calls mine.

My input goes in at the start of a piece of work, in the session's brief. After enqueue, I'm needed only in these cases, each with one phone notification:

  • Screenshots to approve. A check that draws new or changed screens commits them as pending, with a report an AI session writes comparing each with its baseline and with the approved design mockups. I approve or reject them with one command on my own terminal. The command refuses to run without a real terminal, and the queue's instructions forbid AI sessions from running it. An approval that covers a whole set stamps that check itself, so nothing reruns. A rejected set becomes a finding the queue fixes.
  • A stuck branch. Two failed tries at the same step stop the branch, and it waits for me (see failures and improvement). In the period, 50 of the 214 landings got stuck at least once.
  • An exception. I can land a branch past the checks with one command, which names the checks it skips, asks once on a real terminal, and sends me an alarm when it reaches main: a speed bump with an alarm, not a lock. In the period, 19 of 233 landings on main (8%) went in this way, 17 of them during one stall (see results).
  • My calls: putting one branch first on every queue, and restarting a stuck branch once its cause is gone.

My rulings are written down, so later agents keep them

An AI session starts with no memory, so a choice I made last week is, to the next session, just code that looks odd. So each ruling goes into a decisions log, dated and in my words, beside a log of the project's conventions; the queue's own rules carry dated rulings too ("fix everything, ask nothing"). The queue's sessions are told to use them:

  1. A reviewer searches my rulings before filing a finding, so a choice I made isn't reported as a defect for a fixer to undo.
  2. A fix that needs a decision the log leaves open isn't guessed. It goes to the backlog as a question for me, and doesn't hold the branch.
  3. Where a doc states a rule and the code breaks it, the code is the defect. The doc changes only when I change the ruling.

It works only as well as I keep the log: a ruling I never wrote down protects nothing.

A failure a branch causes gets a fix, every failure is logged, and a scheduled task works through the log

How the queue handles a failure, and the loops that turn its failures into changes to itself.

A failure a branch causes gets a fix, never a silent retry

A try is one attempt at one step on one piece of work. A failed try sends the branch to a fix session. Two failed tries at the same step make it stuck: it waits for me, and I get one phone notification. Some failures cost no try, because the branch didn't cause them: running out of the AI plan's usage, a machine problem (a full disk, a lost network), or work that a newer commit replaced. A machine problem holds only that machine.

  1. A test suite that fails runs again, but only the failed tests, each on its own.
  2. A test that fails and then passes, or a screen that draws differently and then matches its baseline on a redraw, is a flake.
  3. If the flake is in a test or screen the branch changed, it is the branch's own failure, and a fix session takes it.
  4. Otherwise the branch is stamped past it, so it doesn't pay for code it didn't write, and the queue opens a new branch from main for the flakes that check met, up to 8 to a branch, since flakes seen together usually share a cause. That branch is enqueued like any other, and only a code change closes it.

Flakes are a real cost. 39 of the 214 landings (18%) were branches the queue opened to fix flaky tests in the project's checks. My rule is that every flake gets fixed at its root, not retried away.

Every step is logged

Every step of every landing is timed, kept on each machine, and shared through the git server for a week: each action's steps, the test suite's stages, each failure with its first error lines and a key that groups alike failures across branches, and what each worker is running now. A record of each landing is committed beside it. Status screens and reports read these logs to answer where the time went and why a branch isn't moving, and the logs are where the queue's speed fixes came from. Two examples: idle branches each kept a full build, 13 to 70 GB, until one day 24 of them held 490 GB of the Mac's 926 GB disk, so the queue now drops the build of every waiting branch. And a check that ran beside the queue's own tests drove the Mac's load to 124 on 15 cores, so the queue now runs at low priority and leaves 4 cores free.

The logs have gaps: landings by exception keep no record, and nothing records time spent waiting for me or for the AI plan's usage to reset.

Three loops turn the logs into changes

  1. After each landing that went wrong (a failed try, a machine problem, or a wait for me), a small AI session (Haiku) reads the run's facts against an open list of process problems before the merge. It says which known problems the landing met and which new ones it found. The code keeps the counts: a problem met twice moves up the list, one met once is dropped a week after it was first seen, and each names the change that would settle it.
  2. A scheduled task works the list. It opens a dated improvement branch, fixes the top problems on it, removes each one it settles from the list, and enqueues the branch, which lands through the queue like any other. 2 such branches landed in the period.
  3. An AI reads past transcripts. New on 10 Nov, so after most of the period: Haiku judges every queue session's transcript for process problems, and Opus checks what it finds against the evidence. A change it proposes to the queue's rules or prompts waits for my approval and never lands on its own, so the judge doesn't rewrite the rules it's judged by without a person agreeing.

Together, the logs, the stuck branches that ping me, the problem list, the scheduled task and the transcript reader make one improvement loop, and its output is work on the queue itself: 106 of the 214 landings (50%) changed its code, tests or AI prompts. 98 came from sessions I started, 6 from the queue's own flake fixes, and 2 from the scheduled task; a few touched the queue only in passing. The records don't say which part of the loop prompted each one.

The queue landed a little less than I enqueued. Over the 18 full days I enqueued 225 branches and 211 landed, through the queue or by me; before the stall it was 125 against 114, after it 76 against 67. So the line of branches waiting grew, though not steadily: it was already long before the stall began, nearly emptied after it, and grew again from 8 Nov to 10 Nov, when I enqueued 53 branches and 27 landed.

I don't judge the queue by a branch's wait, a median 17 hours from enqueue to merge. It counts every hour a branch waited for me, and a screenshot approval asked for in the evening waits until morning; the records don't keep those hours apart. Branches that got stuck, which wait for me by definition, waited a median 30 hours, the rest 14.

What these numbers can't say is whether the queue couldn't go faster or simply wasn't pushed harder: a branch spends most of a day in line either way. The queue's logs record each time a ready check was held and why, which would answer it; I haven't pulled that number out yet.

The low point holds the queue's one long stall: from 2 Nov 17:56 to 4 Nov 13:37, 44 hours, nothing landed through the queue. The Windows PC's disk had fallen below the queue's free-space limit, which holds every Windows check, and every landing needs the Windows stamps. Branches piled up behind it, and I cleared them with 17 landings by exception, among them the branch that freed the disk. A queue that needs every machine to agree is only as available as its least available machine.

Three things limit what the daily and weekly numbers can say. The first and last days and weeks are partial. The queue's code changed throughout, since it lands its own changes, and from 4 Nov every branch also waits for the Linux server's pre-check, which the records don't time on its own. And a day's count mixes branches of every size. The records keep neither the queue's version nor the time spent waiting for me, so they can't say more.

What the queue needs to run, and what it used in the period.

  • Machines: a Mac, a Windows PC and a Linux server, each running one queue worker beside whatever else it does. The queue runs at low priority, so a person at the machine comes first.
  • AI: every AI session runs on my one Claude Max subscription, a flat monthly plan, so there's no bill per session. When the plan's usage runs out, the queue waits, and the wait costs no branch a try. The records don't keep those waits, so I can't say how often the plan's limit held the queue up.
  • What it used: 2,898 AI sessions (2,461 without two unexplained outliers, see limits) and 848 machine-hours of work across the 214 landings, a median 9 sessions and 2.9 hours per branch. Machine-hours count each worker's time on a branch's steps, including AI sessions running beside a check.

Seven ideas worth stealing if you run many AI sessions

None of these depends on what I'm building.

  1. Make enqueue the session's last step, and let nothing after it need a person except decisions only a person can make. (The problem)
  2. Keep the loop in plain code and all state in git, recomputing the next step from scratch each pass, so a crash is cheap. (Code runs the loop)
  3. Give each judgment one fresh AI session with one job, and require fixes to be proven by a test that fails first. (AI for judgment)
  4. Stamp checks on commits and count only a branch's own changes against them, then check main after each landing, so branches don't wait on one another. (Landing in any order)
  5. Write every ruling down where every session must look, so agents that never saw you decide don't undo it. (My part, my rulings)
  6. Log every step and let the queue work on itself: count every failure, schedule branches that fix the most common ones, and have a person approve what an AI judge proposes. (Failures, improvement)
  7. Watch for the one machine that can stall everything. (Results)

Limits

  • Quality isn't measured here. The records count speed and help needed, not what the landed code was like: bugs that got through, or how often main's check after a landing failed. The thin signals are the ones under Results: one landing fixed a failed check of main, and git shows two reverts.
  • One project, one developer, 20 days. These are my queue's numbers on my project, not a benchmark. The queue's own code changed throughout, since it lands its own changes, so the period mixes versions of it.
  • Enqueue to merge is wall-clock time, waits included. It counts time spent waiting for my approvals or help, and for busy or broken machines, and the records don't split those out.
  • Exceptions aren't in the records. The 19 landings I made by exception kept no record, so the charts and tiles cover the 214 landings that went through the queue (the queue-length counts do include them). a small file on a branch naming a check and the commit it passed on

merging main into a branch, to resolve a conflict or to bring it up to date

The data, and how this page was checked

  • Records: one record per landing, written by the queue just before each merge: for each worker, how many AI sessions it ran, its failed tries, the machine problems it met, its seconds on the branch's steps, and whether the branch was stuck there. 214 records, 23 Oct to 11 Nov 2026 US Pacific time, which is every landing since the queue started keeping them. The every-landing download under the daily chart has every one, each branch reduced to its kind and origin.
  • Enqueue and merge times come from the git history: each branch's first enqueue marker and its landing merge on main. A branch enqueued again after more work keeps its first time.
  • Kind and origin come from the branch name: the queue names the branches it opens for flakes and for failed checks of main with their own prefixes, and the scheduled task names its improvement branches its own way. Every other branch came from a session I started.
  • Percentiles interpolate between ranks (the inclusive method).
  • Exceptions are the landing merges on main in the same period that carry the exception mark.
  • Enqueued counts the branches enqueued each day, whether they have landed yet or not; a landing by exception that was never enqueued isn't counted. In the line, or in the queue at noon, counts the branches enqueued and not yet merged at noon each day, stuck or not: recorded landings, landings by exception that were enqueued first, and branches still queued when I took the data. Days are calendar days in my time zone, except that 23 Oct also counts the one branch enqueued late on 22 Oct. A full day is any but the first and last, which are partial; the medians use full days only. The download under the chart has one row per day.
  • Changed the queue counts a landing whose merge changed the queue's code, its tests, or its AI prompts.
  • From me, not the records: the scheduled task, the transcript reader and the Claude Max subscription are my description of my setup; the scheduled task's branches are in the history. The transcript reader is newer than most of the period, and its effects aren't measured here. The stall's cause comes from the notes I wrote on my exception landings that day.
  • The mechanism was checked against the queue's code and design notes on 12 Nov 2026: the order of the rules, the limits in the steps (look intervals, claim times, two tries, eight flakes to a branch), and which model runs which session. The code and notes belong to a private project and aren't published.
